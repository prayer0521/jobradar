# jobradar

抓国内大厂公开招聘岗位，用大模型分析行业缺什么人才、该学什么。

有网页版和命令行两套入口，共用同一个数据库和同一套业务逻辑。

## 网页版

```bash
./jr 服务
```

打开 http://127.0.0.1:8787 ，三个页面：

| 页面 | 作用 |
|---|---|
| 总览 `/` | 岗位总数、方向分布、公司×方向、近 60 天趋势、**分析覆盖率** |
| 分析报告 `/report.html` | 渲染报告正文、历史报告列表、两份报告对比 |
| 任务 `/tasks.html` | 手动触发抓取/分析、看实时进度、配置定时抓取 |

只绑 `127.0.0.1`，没有鉴权 —— 别把 `JOBRADAR_HOST` 改成 `0.0.0.0` 暴露到公网，
触发分析的接口会消耗你的模型配额。

换端口：`./jr 服务 --port 9000`。

### 关于分析按钮

分析要花钱，所以点之前页面会先告诉你要烧多少次模型调用：

```
开始分析（预计 20 次模型调用）
选中 300 个，其中 15 个已缓存，需新抽取 285 个。完成后覆盖率 0.27% → 5.41%
```

有个反直觉的点：**重复点分析不会提高覆盖率**。取岗位是按发布时间倒序取最新
N 个，第二次点还是同一批，全部命中缓存、零调用、报告一模一样。想分析更多岗位
必须调大 limit（后端+算法方向共 1224 个可分析）。

抓取不花钱，可以随便点，也可以开定时。**定时只抓取，不会自动分析。**

## 命令行

```bash
./jr          # 抓取 + 分析 + 出报告
./jr 抓        # 只抓岗位
./jr 报告      # 只分析（用库里已有数据）
./jr 看        # 看库里有多少岗位
./jr 服务      # 启动网页版
```

英文别名一样能用：`crawl` / `report` / `stats` / `serve`。

常用参数（放命令前后都行）：

```bash
./jr 报告 --limit 300          # 分析 300 个岗位
./jr 抓 --companies tencent    # 只抓某家
./jr 抓 --max-pages 100        # 抓满（默认 30 页抓不全百度和网易）
./jr 报告 --tracks ai          # 只分析 AI 方向
```

## 配置

`.env`：

```
ANTHROPIC_BASE_URL=https://console.tars-ai.com
ANTHROPIC_AUTH_TOKEN=sk-...
JOBRADAR_MODEL=claude-opus-5
```

四个实测踩过的坑：

- 鉴权必须用 `Authorization: Bearer`。改成 `x-api-key` 会被这个中转站路由到
  别的后端模型（实测返回 `gemini-3.1-flash-lite`），拿不到 Claude。
- 这个中转站不支持 assistant 预填，所以结构化抽取走 `tool_use` 强制调用，
  不是让模型自由输出 JSON 再解析。
- **opus 系列废弃了 `temperature`**，传了直接 400。代码里默认不传。
- **opus 有时把结果写成 `<thinking>` 文本而不调工具**，那一批会整个丢弃、
  配额白烧。提示词里明确禁止了，重试时还会追加一条硬性指令。

`/v1/models` 可以查可用模型。想省钱换 `claude-haiku-4-5-20251001`，
质量差别明显：haiku 会漏掉"样本偏斜"这类自我限定，opus 会主动指出。

## 招聘类型

默认抓**校招 + 实习**。要社招得显式指定：

```bash
./jr 抓                        # 校招 + 实习（默认）
./jr 抓 --type campus          # 只要校招
./jr 抓 --type intern          # 只要实习
./jr 抓 --type social          # 社招
./jr 报告 --type campus        # 只分析校招
```

不支持某个类型的公司会自动跳过（比如网易没有校招接口，抓校招时不会白跑）。

**`--max-pages` 是总页数预算，不是每种类型的页数。** 百度这类"一次请求只能取一种
类型"的站点，页数用完就轮不到后面的类型了 —— 抓多类型时要放大，比如 `--max-pages 120`。

各家怎么切换招聘类型，规律性很弱，全靠实测：

| 平台 | 切换方式 |
|---|---|
| 飞书招聘 | **请求头** `website-path: campus`（body 里的参数试遍都没用） |
| 百度 | `recruitType` = `SOCIAL` / `GRADUATE` / `INTERN`（校招是 GRADUATE 不是 CAMPUS） |
| 小红书 | `recruitType` = `social` / `campus` / `intern`（必须小写） |
| 网易 | `workType` = `0` 社招 / `1` 实习（没有校招值） |
| 腾讯 | 校招在 `join.qq.com`，另一套接口和字段，按 `projectId` 分校招/实习 |
| MokaHR | 换 `siteId`，每种类型一个独立站点 |

### 两个排查很久的坑

**飞书招聘按 User-Agent 拦截。** 带 Windows 或 Linux 的 UA 一律返回 405 空 body，
换 Mac UA 就正常，与 Chrome 版本无关。405 + 空 body 很像"方法不允许"或 CSRF 门禁，
实际是 UA 黑名单。项目默认 UA 是 Windows，所以 `feishu.py` 里按请求覆盖成 Mac UA。
以后再遇到 405，先换 UA 再怀疑别的。

**大疆的响应是加密的。** 返回 `{"data": "<base64>", "necromancer": "<16位hex>"}`，
AES-128-CBC，**key 就是 `necromancer` 字段本身**（16 个 ASCII 字符直接当密钥），
IV 是页面里的 `aesIv` 常量。另外 `jobStats.total` 恒为 0，不能拿来判断翻页。

这些需要绕过登录态或风控，本项目不做。B站和快手是最接近的两个——如果你能从浏览器
抓一次真实请求（F12 → Network → 复制 cURL），补上缺的参数或 token 就能接。
在 `jobradar/spiders/` 下加采集器并 `@register` 即可。

飞书招聘是共享平台，接新公司只要继承 `FeishuSpider` 填 `host`：

```python
@register
class FooSpider(FeishuSpider):
    slug, company, host = "foo", "某公司", "foo.jobs.feishu.cn"
```

试租户是否存在：`curl -X POST https://{租户}.jobs.feishu.cn/api/v1/search/job/posts`
（记得带 Mac UA），返回 400 说明没这个租户。

## 工作原理

分两阶段，不是把几千条 JD 一次塞给模型：

1. **抽取** —— 每 15 条 JD 一批，模型通过 `tool_use` 提交结构化标签（技能、领域、
   职级、信号），同义词归一（k8s→Kubernetes、大模型→LLM）。结果按岗位指纹缓存，
   下次不重复花钱。
2. **统计 + 解读** —— 用代码算频次，再把频次事实喂回模型做解读。结论有据可依，
   而不是模型凭印象编。

岗位方向分类（`backend` / `ai` / `other`）是本地规则判定，见 `jobradar/models.py`。

**分析默认按公司轮转取样**。岗位数在各公司间极不均衡（字节占可分析池 70%），
直接按发布时间取 300 条只能覆盖 6 家、字节+小红书占 92%，腾讯/大疆一条都取不到，
报告会变成"字节招聘分析"。轮转取样后 300 条覆盖全部 9 家、每家约 37 条。

## 架构

```
jobradar/
  config.py    路径配置，全部基于项目根绝对化
  db.py        连接管理 + 迁移。每次操作开新连接，WAL 模式
  models.py    Job 数据结构 + 方向分类器
  http.py      限速 HTTP 客户端 + 跨进程抓取锁
  spiders/     三个采集器 + 注册表
  store.py     SQLite 读写，upsert 分批提交
  llm.py       Anthropic Messages 客户端
  analyze.py   抽取提示词 + 频次聚合 + 报告提示词
  service.py   编排层，CLI 和 API 共用（这一层不打印任何东西）
  tasks.py     后台任务运行器，全局单槽
  scheduler.py 定时抓取
  api/         FastAPI 路由与响应模型
  cli.py       命令行
web/           静态前端，无构建步骤
```

几个设计决定：

- **每次数据库操作开新连接**，不共享。共享连接会串扰事务 —— 实测线程 A 未提交的
  行会被线程 B 的 commit 一起提交。开连接只要 17µs，是查询耗时的 0.3%。
- **WAL 模式** + upsert 分批提交（500 行或 5 秒），所以抓取进行中刷新页面不会
  `database is locked`。
- **全局单槽任务**，同时只跑一个。并发抓取对目标站是双倍压力，抓取与分析并行会
  让分析读到抓一半的数据。忙时直接返回 409 而不是排队。
- **跨进程文件锁**：服务在抓取时你又开终端敲 `./jr 抓`，第二个会被挡下。
- **报告存数据库**而不是文件，因为要支持历史列表和对比。CLI 的 `--out` 仍然写
  文件，但那是导出，不是真相来源。
- **进度用轮询不用 SSE**：分析每批才动一次，可能几分钟，1 秒轮询够了，省掉跨线程
  桥接和断连处理。

## 测试

```bash
python3 -m pytest tests/ -q
```

111 个测试。重点覆盖的是踩过的坑：并发读写不丢数据、写事务不阻塞读、共享连接的
事务串扰、腾讯中文日期排序、任务槽位释放的竞态、配额错误立即中止、覆盖率快照
用抽取后的计数。
